# 阶段三完成说明：API 直连生成

> 目标（路线图原话）：**API 直连自动生成（多提供商、缓存去重、失败降级引导）**。
> 阶段一实现了「模式 A：网页聊天导入」，这一阶段补上「模式 B：应用内直接调 API」。
> 两种模式产出同样的数据结构，**入库之后无差别使用**。

## 一、一句话结论

设置页填好「提供商 + 地址 + 模型 + 密钥」之后，「加入」页顶部多出一个
**分段按钮（网页聊天导入 / API 直连）**：切到 API 直连，输入单词点「生成卡片」，
返回的 JSON 会被直接填进原来那个粘贴框 —— 解析、校验、去重、补干扰项、入库
全部复用模式 A 的代码，一个字都没有重写。

**数据流**：

```
单词 + 模板 + 语言
   ↓ 模板 build()（模式 A 用的同一套模板）
最终 Prompt
   ↓ sha256(地址 + 模型 + Prompt) → 查 wc_api_cache
   ├─ 命中且未过期 → 原文 → CardParser → ParseResult
   └─ 未命中 → POST {base}/chat/completions → 原文 → 同样解析 → 写缓存
   ↓
填进「加入」页的粘贴框 → 走模式 A 的校验 / 去重 / 入库
```

设置页按地址反查是哪一家（认不出来就显示「自定义」）。

## 四、错误分类：每一种都要说清「下一步」

失败类型是 `AiFailureKind` 枚举，界面上一定显示「原因 + 怎么办」：

| 情况 | 类型 | 文案要点 |
|---|---|---|
| 地址 / 模型没填 | `notConfigured` | 去设置页填，或继续用网页聊天导入 |
| 地址不是合法链接 | `badRequest` | 给出正确写法 |
| 400（含服务端自己的 message） | `badRequest` | 「多半是模型名写错，或地址少了 /v1」 |
| 401 / 403 | `unauthorized` | 检查密钥过期、多余空格；本地模型可留空 |
| 404 | `badRequest` | 地址一般填到 /v1 |
| 429 | `rateLimited` | 等一会儿，或一次少生成几个词（可重试） |
| 5xx | `serverError` | 等一会儿重试，或换一家（可重试） |
| 连不上（含本地服务没起） | `network` | 检查网络 / 代理 / 本地模型（可重试） |
| 超时 | `timeout` | 调大超时、换小模型、少给几个词（可重试） |
| 200 但不是 JSON / 没有 choices | `badResponse` | 确认是 OpenAI 兼容接口 |
| 内容为空（或被长度截断） | `emptyContent` | 截断时提示少给几个词 |
| 拿到了内容但不是卡片 | `unparsable` | 交给解析器报「第几张卡片缺什么字段」，**原文保留** |

两个实现细节：

- 解码用 `utf8.decode(bodyBytes)` 而不是 `response.body` —— 很多服务端不发
  `charset`，`http` 包会按 latin1 解，中文释义会变乱码；
- 400/401 这类错误优先显示**服务端自己返回的 message**（各家字段位置不同，
  `error.message` / `error` / `message` / `msg` 都认），实在没有才给正文片段。

## 五、缓存与去重

- 新表：`wc_api_cache(key, response, model, prompt_tokens, completion_tokens, created_at)`，
  和别的 `wc_` 扩展表一样放在同一个 `collection.anki2` 里，Anki 会忽略。
- 缓存键 = `sha256(地址 + 模型 + 最终 Prompt)`。换模型、换地址、改模板（哪怕一个字）
  都会得到新键 —— **不会拿旧答案糊弄**。只差首尾空白和结尾斜杠时算同一个键。
- 缓存时长用设置里的 `apiCacheHours`：**0 = 不缓存**；过期条目读到时顺手删掉。
- 缓存的是**模型原文**而不是解析后的卡片：以后解析器变聪明了，旧缓存也跟着受益。
- **解析失败的响应不写缓存**：下次重试说不定就正常了。
- 命中缓存时不记调用次数、不计 token、要在界面上明说「这次没请求 API、也没花钱」。

## 六、失败降级引导回模式 A

这是路线图里点名要的东西，落在「加入」页的结果条上：

1. 失败时显示 **原因** + **下一步**（见上表）；
2. 只要拿到了原文（模型答非所问、格式不对），**原文自动填进粘贴框** ——
   用户可以直接手改后入库，这一步完全不依赖网络；
3. 结果条上有「**改用网页聊天导入**」按钮：一键切回模式 A，
   并把选择写进设置（`preferManualMode`），下次打开还是模式 A；
4. 没配 API 时切到 API 直连会先给一条灰底提示，去设置页补齐，或者切回去。

反过来，模式选择也会记住：配好 API 之后默认就是 API 直连，手动模式也不会被
「已经有凭据」顶掉。

## 十、已知限制与取舍

- **API Key 是明文存在本机的 `wc_settings` 里**。这是本机单用户应用的既有取舍
  （数据完全不出设备），界面上写明了「只存在这台设备的数据库里，不会上传」；
  要更强的保护得引入平台密钥库（`flutter_secure_storage`），不在这一阶段。
- **缓存不区分"同一个人"**：同一台设备同一个 Prompt 就算命中，符合本机应用的定位。
- **不传 `max_tokens`**（默认 0 = 不传），让服务端用自己的默认值；
  被长度截断时结果条会提醒「可能有卡片没生成完整」。
- **不做流式输出**：一次生成的单词量本来就小，流式只增加复杂度。
- **没有"自动重试"**：429/5xx 只给「重试」按钮，不偷偷重发（避免重复计费）。
- **模式 A 的解析器一行没改**，所以模式 B 的容错能力完全等于模式 A。
